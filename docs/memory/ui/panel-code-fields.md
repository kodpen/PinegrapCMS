## How does a panel screen draw a code field?
- `pg_code_editor_attach(array('id' => 'code', 'code_type' => 'css', 'readonly' => false))` (`includes/fn/editor.php`) after the textarea: the facade's editor (`assets/js/pg_code_editor.js`, CodeMirror 6) takes the textarea's place and keeps its value current, so the form submits as before and the save path does not change. `code_type` takes the names `get_codemirror_javascript()` took (`mixed`, `css`, `javascript`, `application/json`, `php`, `xml`, …); `pg_code_editor_language()` maps them to the four grammars (`css`, `javascript`, `json`, else `html`). Optional `height`; without it the editor grows with the text, as the textarea did.
- The helper prints `pg_code_editor_includes()` once per request (the facade script and `PgCodeEditor.configure({ bundle, phrases })`); the engine bundle (~600 KB) is fetched on the first editor only. The engine's own texts come from `pg_code_editor_phrases()` (`lang()`, the same keys `_sdCodePhrases()` uses in the designer); the inline JSON is `pg_code_editor_json()` (`JSON_HEX_TAG`, so a phrase cannot close the script).
- F11 fills the window with the editor (`.pg-code-field-full`, `body.pg-code-field-open`), Esc leaves. The instance is kept in `window.pgCodeEditors[id]`; a screen that changes the language after a file name calls `pgCodeEditors.code.setLanguage()`.
- The field's panel look is `.pg-code-field` in `backend.src.css` (border and radius like a form control, 12rem minimum); the designer's panes and the code dialog carry only `.pg-code-editor` and are not touched by it.

## What does 'code_editor' => false do, and when is it set?
- `pg_page_shell()` / `output_header()` with `'code_editor' => false` leaves CodeMirror 5 and its linters (40 files, ~2 MB) out of the head and parks the tags in `<template id="pg-code-editor-assets">`; `window.pgCodeEditorReady(markup, done)` (`backend.src.js`) loads them when markup that mentions CodeMirror arrives later (a Site Settings pane with a code field). A screen whose own code fields are the facade's sets it, so the page pays for neither editor until one is drawn.
- Still on CodeMirror 5 (head includes + `get_codemirror_javascript()`): the content screens (`add_/edit_custom_style`, `_dynamic_region`, `_designer_region`, `_login_region`, `_field`, `_product_group`, `edit_javascript`, `edit_theme_css`, `create_file`, `edit_form_*_view`, `view_system_style_source`), the settings panes (`includes/settings/*.php`), `view_folders.php` (its own instance for the inline file editor, released with `pgReleaseEditors()`), `page_designer.js`, `theme_designer.php`, `product_builder.php`, `backups.php`, `smtp_settings.php`. Each moves the same way as `edit_file.php` did: the attach helper, the property, and whatever used the CM5 global `editor` (`create_file.php` switches the mode after the file name) rewritten on the instance. When the last one has moved, `get_codemirror_includes()`, the template, `pgCodeEditorReady()` and `assets/lib/codemirror/` go.

## How does the colour scheme reach the editors?
- The server reads the `prefers-color-scheme` cookie (`pg_code_editor_theme()`) for the first paint; the panel's scheme switch (`setTheme()` in `backend.src.js`) pushes `dark`/`light` to every open CodeMirror 5 instance and, through `window.pgCodeEditors`, to every facade editor (`editor.setTheme()`), so a switch needs no reload.
