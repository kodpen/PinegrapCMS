## How does the offer editor save?
- `edit_offer.php` + `edit_offer_f.php` + `assets/js/offer_editor.js` share one state object: the offer, condition rows, result rows. Save is a single JSON request (`api.php` -> `action: offer_editor`, `type: offer_save`).
- It is exempt from the general role gate in `api.php`; `pg_offer_editor_handle()` grants access itself with `validate_user()` + `manage_ecommerce`.

## What four rules apply?
- No name is asked. `offer_rules.name` / `offer_actions.name` are generated by `_pg_offer_auto_name()`. Never add a name field to the screen.
- A shared row is copied. If another offer also uses the rule or action row, write INSERT, not UPDATE (`_pg_offer_rule_write()` / `_pg_offer_action_write()`); a row whose link was cut is deleted if nobody else uses it.
- Type registries are two-sided. A new condition/result type goes into `_pg_offer_condition_types()` / `_pg_offer_action_types()` AND the JS side; if either is missing the type can neither be added nor saved.
- Children first, `offers` last. No transaction (the code opens none, and a table over the 2026.4.8 limits may still be MyISAM: `data/table-engines-and-row-size.md`); validation (`_pg_offer_validate()`) finishes without writing anything, so the write order is never broken.

## How is the currency symbol handled?
- `BASE_CURRENCY_SYMBOL` holds HTML as an entity (`&#8378;`). Output to screen and JSON goes through `_pg_offer_currency()` (i.e. `html_entity_decode`); printing the raw constant prints the literal `&#8378;`.

## How is a percentage written?
- Through the `'{var:1}%'` key (Turkish `%{var:1}`): `_pg_offer_percent_text()` on the server, `percentText()` with the `L.percent` template (`{n}`) in `offer_editor.js`. The tier and shipping texts take the formatted figure as a var. A `'%'` glued in code read "%10 off the order" on an English panel (#3030).
