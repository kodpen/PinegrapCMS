## Which steps are there?
- SF1 (M) Address autocomplete. SF1a (drivers, `address_suggest.php`, settings card, tests) in progress; SF1b (the form hooks: checkout, address book, panel form) after #5078 merges.
  - Drivers `includes/geo/autocomplete/<key>.php` (`google_places.php`: Autocomplete plus Place Details with a session token; `mapbox.php`: Geocoding v6; `photon.php`: an OSM Photon host, the public one by default), each `pg_addr_<key>_suggest($text, $country, $lang)` and `_fill($id)` returning one shape (street, street 2, city, district, state, postcode, country code); `pg_addr_providers()`, the key sealed in Settings › Ecommerce › Addresses with a Test box. `address_suggest.php` (root): POST with the session token, rate-limited by its own WAF bucket, answers at most 5 suggestions; no key or provider script reaches the browser, so the cookie notice needs nothing. The site hook in `pg_ship_to_district_script()`'s file: a suggestion list under the street box (listbox keys), a pick fills the boxes through the labels-by-country rule (`commerce/address-labels-by-country.md`: a Turkish pick writes the district into the city box), the state pick list matched by name or `plate_code`; the account address book and the panel's `verified_shipping_address_form.php` get the same hook; the typed address always wins. Tests: each driver's answer mapped from a fixture, the TR mapping. Memory: `commerce/address-autocomplete.md`.

- SF2 (S) Accessibility statement. Done in PR #5053.
  - A system widget `accessibility_statement` (`includes/fn/widgets_accessibility.php`, palette entry, starter layout): the statement text from a settings card (Settings › Accessibility: organisation name, scope, contact address, feedback mechanism, enforcement body text, the date) and from the nightly report (`includes/fn/a11y.php`: conformance claimed as full / partial / none by the open findings' severities, the known limitations listed by rule concept with the page count, the last check date), in the W3C statement structure; a classic `?statement=1` print view; the report screen links "Create the statement page". Tests: the conformance verdict from fixed finding sets. Memory: `platform/accessibility-statement.md`.

- SF3 (M) Site search tuning. After question 1.
  - Migration sub-step for `site_search_daily`; the search widget (`includes/fn/widgets.php`, the `search_items` branch) counts each search once per visit and term into the rollup with the result count (zero results kept apart) by the counter rules of `visitors/high-volume-counter-rules.md`; a result click sends the term and the item through the page-view beacon (`visitors/page-view-beacon.md`), counted as a click. Synonyms (`config.search_synonyms`: groups of words, applied to the query by `pg_search_expand()`, pure) and promoted results (`config.search_promoted`: term → page, product or record pinned first, marked "Recommended"); Site Settings › Search edits both. A "Site search" section for the Visitors overview (`plans/visitors-overview.md`; until V1 lands, `visitor_search.php` from the flyout): top terms, zero-result terms with a "promote" shortcut, click-through. Memory: `visitors/site-search-rollup.md`, `designer/search-synonyms-promoted.md`.
