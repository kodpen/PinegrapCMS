## Which steps are there?
- S under 400 product lines, M about 1,000; each step its tests and its memory topic in `workspace/`; a schema step rerun twice on a dev DB. A5-A8: `agent-channel-steps-2.md`.

- A0 (S, `tools/` only) Door experiment, no site change. `done` (#7969): `workflow/agent-channel-experiment.md`. Which doors wake a cloud session: a plain `POST` to a session's inbound webhook (`watch_url`: does it need the sealed secret, what arrives), a routine `/fire`, and `tools/ws_wait.php` (waits on `GET /workspace/sync` with ETag for a matching message, in the cloud); `tools/ws_post.php`; a GitHub Actions step posting `[ci]` and `[ready]` to a private channel on dev.pinegrap.com with per-agent application keys. Result in `workflow/agent-channel-experiment.md` within days: it fixes A3's door fields.
- A1 (S) Claude routine hardening. `done` (#7970): `workspace/workspace-claude-instructions-version.md`. A claim refuses a run that has not read the current instructions (409 `instructions_outdated`, a system line), the instruction version on the card, a guide warning (`workspace/workspace-claude-bootstrap.md`).
- A2 (S, done, #7968) Replies and "no answer needed". `parent_id` on `workspace.messages.create` (a thread as the panel makes it, `api/api-endpoint-rules.md`); "no answer needed" on Claude's answer route closes the request without a message.
- A3 (M, schema) Agent registry, membership, doors. After A0 and A2. A table of agents (kind, handle, name, avatar, application id, provider, model, sealed key, status; the door: kind push or poll, URL, sealed secret, failures, last knock; the schedule: every N minutes, next time, note; the handle unique and never a person's user name) and a channel-agent row (allowed, wake rule, the tier the channel's manager allows, default tier 1, the loop-guard switch); the @ picker, tags, `ws_message_ask_assistants()`, the discussion follow and the settings read `ws_assistants()` from it; the agent card with its door and schedule; today's Claude routine becomes the first push agent; the membership routes (add or remove an agent in a channel; only a member adds one to a private channel); `claude_access` and `ai_access` stay. The depth and hourly brakes.
  - A3 `done` (#8038): tables, Claude's row, routes, brakes.
  - A3b `done` (#8189): the Agents card in Workspace settings (`workspace/agent-registry.md`).
  - A3c (S) after A3b: the channel's agents list in the channel settings (workspace.js) on the membership routes.
- A4 (M) Request queue, push and scheduled wakes. After A3b. A matching message makes one `ws_ai_requests` row per agent (`app:<id>`, `model:<id>`), shown on the message; a wake row (kind `wake`, with its note, no message) when a schedule is due or `at <time>` comes, made by the general cron job (`fn/cron.php`, `job.php`); a push door is knocked at once with ids and the site address only, retried with backoff, its failures on the card. `GET /workspace/agent-requests`, a claim with 409, answer and fail routes generalising Claude's; the brief (preamble, context, memory digest, the loop-guard text unless switched off, the site's MCP address and the agent's scopes: the channel tools are the API's routes as MCP tools, `api/api-mcp-server.md`, no second catalogue); `/wake @agent every 30m "…"`, `/wake @agent at 21:00 "…"`, `/wake @agent off` in the channel and the same through the API, an agent for itself; an agent edits or deletes only its own messages, with an edited mark. Memory: `workspace/agent-doors.md`.
  - A4a `done` (#8221): rows, brakes, knock, request routes. A4b: the rest (`workspace/agent-doors.md`).
