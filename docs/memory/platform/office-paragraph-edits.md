## How is a paragraph of a document changed?
- The same read with `edit` as a workbook (docs/memory/platform/office-cell-edits.md): `pg_office_docx_read()` marks each drawn paragraph with its position among all `w:p` of word/document.xml in document order (`data-p`, `pg_office_docx_paragraphs()`, the same count the save uses) and, when it cannot change, why (`data-lock`); `edit.paragraphs` holds the plain text of those that can, by position, and `version` the sha1 of the bytes.
- `pg_office_view.js`: a click picks a paragraph, a second click (a double click too, with its word selected), Enter or F2 opens it in a box at the click; Enter keeps and goes to the next, Shift+Enter is a line break, Tab/Shift+Tab move, Esc undoes, Ctrl+S saves. The text typed so far already counts, so Save takes it before Enter (the grid does the same now). A changed paragraph shows plain until saved; links follow only with Ctrl/Cmd.
- Saves: `explorer_file_save` with `paragraphs` ([{p, text}]) and `office_version`; in a channel `ws_file_office_save` with `paragraphs`, into a copy (docs/memory/workspace/workspace-office-edits.md). `pg_office_docx_save()`: same lock, version check, copy-build-verify-rename as cells (`pg_office_save_package()`); only word/document.xml is rewritten (DOM, no blank dropping).

## How does new text go into the runs?
- Text is what a person types: `\t` a tab, `\n` a line break (`w:br`, `w:cr`), U+2011 / U+00AD the non-breaking and optional hyphens. `pg_office_text_hunks()` keeps the common start and end whole words at a time (word/number/space/char tokens: #1149, "BIG" before "BOLD" went into the bold run when taken by letters), compares the words between (LCS; a middle over 250000 cells, or past the save's 2000000 budget, is one change), then each change gives back the letters its old and new words share, start first (`pg_office_text_hunk_trim()`, #1158: "aple" to "apple" is `p` added, so a word split over bold, subscript or link runs keeps them). Changes go into the runs they cover; untouched runs keep their XML. Added text joins the run of the character before it, except right after a link (textless runs closing the link count as it): then the run after; at the paragraph end or before another link, a new run formatted like the mark minus `rStyle`/`vanish`/`specVanish` (#1149, #1158). A replacement takes the formatting of its first character, as Word does. Emptied runs go; a paragraph without runs gets one formatted like its mark. Runs are never merged into the first run's style.

## What is never changed?
- Paragraphs with tracked changes (also formatting changes waiting for review), fields (page numbers, dates, TOC, `fldSimple`), comments, foot/endnote marks, pictures/shapes/equations/symbols, page or column breaks, content controls, smart tags, anything unknown; and by place: inside a content control or custom XML, a text box, a cell merged into another (`vMerge`/`hMerge` continue). Whole documents: signed, protected (`documentProtection` enforced with edit not none, `writeProtection`), Track Changes on, main part over 8 MB (the preview reads its beginning only) or settings that cannot be read (docs/memory/platform/office-dom-ceiling.md), not UTF-8 or with a DOCTYPE (`edit.why`). 2000 paragraphs a save, 100000 characters a paragraph.

## What was checked, and what not?
- `tests/office_edit_test.php`; 24 Word-written documents (Apache POI test data) and python-docx/LibreOffice ones: untouched paragraphs byte-identical (C14N), new texts read back by python-docx and LibreOffice 24.2, namespace declarations kept; sandbox with Playwright (file window, conflict, protected document, Quick Look, Workspace replace and copy, dark theme). Not checked: Word itself, Pages, Google Docs.
