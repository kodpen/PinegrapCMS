## Which branch?
- Work branches start from `development`; PRs target `development`. `main` carries released versions only: never open a PR to `main`, never merge or rebase `main`. The release PR is the owner's.
- Threads squash-merge their own CI-green PRs into `development` (standing owner approval); releases to `main` and version numbers stay the owner's.

## Who does git?
- One hand does all repo actions (branch, commit, push, PR, issue): the session with git and GitHub access. An agent that only edits code leaves its change in the working tree and produces no bundle or hand-off file (no `dev/_handoff/`).

## Commit author and messages?
- Author `Erdal Güral <erdaltyy@gmail.com>`. Messages describe the change and its technical reason only, with no AI or session trace (see CLAUDE.md rule 2). If the commit identity cannot be set, squash-merge with an explicit title and message so the `development` commit is authored correctly.

## Where does the "Generated by Claude Code" PR footer come from?
- A cloud session's GitHub proxy appends `---` / `_Generated by [Claude Code](…)_` (with or without the session link) to every PR body it creates or edits, through `pulls/<n>` and `issues/<n>` alike (tested 2026-10-20). Claude Code also asks for `Co-Authored-By:` / `Claude-Session:` commit trailers. `.claude/settings.json` turns all of it off: `attribution.commit` and `attribution.pr` empty, `attribution.sessionUrl` false.
- A cloud session reads that file only when it starts inside the clone of its one repository; so does a thread of a Projects project with one repository. A session with several repositories, or one whose repository was added after it started, does not: for the organisation account the same `attribution` block sits in the server-managed settings, next to `channelsEnabled` (claude.ai › Organization settings › Claude Code › Managed settings, Owner role). Footers kept appearing anyway, so a thread cannot count on either.

## Who removes the footer?
- Not a cloud thread: an API edit comes back with the footer, so do not retry it. Keep it out of `development` by squash-merging with a hand-written title and message.
- A session linked to the owner's computer: in the Claude app's built-in browser, signed in to GitHub as the owner, PR › description `⋯` › Edit, delete the last two lines, Update comment. That request does not pass the proxy, so it sticks until a cloud session edits the body again. On 2026-10-20 every open PR and 235 closed ones were cleaned this way.
- Owner's rule (2026-10-20): when needed the linked session takes over merging and cleans each PR body before it merges; cloud threads leave the footer alone.

## How do I edit shared files?
- Shared files: `includes/local/tr.json`, `pinegrap/changelog.txt`, the open version's migration file, `init.php`.
- Append only, in your own section; never rewrite the whole file.
- Right before writing: `git fetch origin development && git merge origin/development`. Right before pushing: rebase on `development`; keep both sides' sections on conflict.
- `docs/memory/README.md` is generated: never edit or merge it by hand; run `php tools/memory_index.php` after the merge.

## Which files belong to the API and which to ERP?
- The external API: `includes/api/**` (webhook delivery is `includes/api/outbound/webhooks.php`), `integration.php`, `api_settings.php`, `api_docs.php`, the jobs `api_webhook_job.php` and `api_sync_job.php` (`api.php` is the panel's action endpoint, not the API). ERP: `includes/erp/**` and the root `*erp*.php` screens. ERP reaches the API only through `includes/erp/api.php` (`erp/erp-api-seam.md`) and edits no API file; what one side needs from the other is asked of that side.
