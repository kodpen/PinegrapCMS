## Where are the rules and the earlier parts?
- `decisions-made.md`; its Parts line lists the files. Entries name the issue, the date and the migration shape.

- A narrower scope asked on an OAuth refresh (#6999, owner, 2026-11-05, option A; the architect had recommended keeping today's accepted-but-not-applied behaviour, which RFC 6749 §3.3 allows since the answer's `scope` names the real set, and the owner chose the column): `api_devices.access_scopes TEXT NULL` by `install_add_column()` in one re-runnable sub-step under the next free API label of `2026.11.0.php` (`11.0.71`-`11.0.79`, read at push). NULL means the consent applies: every running row, every team device row, every refresh sent without `scope`. Shape (architect): `pg_oauth_token_from_refresh()` hands the asked set ∩ the consent (a JSON list like `scopes`, NULL when `scope` was not sent) to `api_device_rotate_pair()`, which writes it in its one conditional UPDATE (the device route passes NULL), and answers with it; request auth in `includes/api/devices.php` takes `pg_oauth_effective_scopes()` ∩ `access_scopes` when the column is not NULL, so the ceiling and the person's rights still apply. The consent column `scopes` never changes and `connected_apps.php` keeps showing it, so the next refresh may ask for all of it again (RFC 6749 §6); asking for more stays 400 `invalid_scope`. Concurrent refreshes with different `scope` values get the same derived access token (`api/api-device-refresh-rotation.md`): the row's last write rules, a replay within the 60 s grace sees it; written there. Test: a pure function resolving the set from consent, asked and stored values (`tests/oauth_test.php`). Reason (owner): one column, idempotent, invisible to running sites; a client asking for less gets a token holding less. Refused: overwriting `scopes` (the connection narrows for good, against §6), a JSON object in `scopes` (every reader of the column changes).
